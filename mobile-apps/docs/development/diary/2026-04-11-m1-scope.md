# 2026-04-11 — M1 scope settled: volume control + onboarding wizard

## Summary

M1 is **the volume control**, implemented on both `alloy-ios` and
`alloy-android`, gated by a **first-launch onboarding wizard** that
discovers AV receivers via two channels: directly on the LAN, and
through the user's Home Assistant instance. The user picks one from
the combined list and binds it as their volume target. No other Alloy
feature is in M1.

## Why the volume control is M1

The volume control is the single most important surface in Alloy for
three reasons: it's the most-used control by a wide margin, it's the
*canonical implementation* of the app-wide UX principles (optimistic
UI with decoupled intent and confirmed state, instant load, background
work), and every other feature in the product plan explicitly inherits
its interaction model. Putting it first means:

- the hardest interaction problem in the app gets solved *first*,
  not last;
- the shared spec format — the bet at the heart of the dual-native +
  AI-transpile strategy — gets road-tested on a small, tractable
  surface;
- the architectural patterns (dual-value state model, throttling,
  instant load, target abstraction) all land before anything else
  has to lean on them;
- it's demonstrable in thirty seconds, which matters for dogfooding.

There's also a personal reason: the user has been frustrated with
existing volume controls — the Denon control app especially — for a
long time. M1 exists, in part, to fix exactly that frustration.

## How the onboarding wizard got added

The original M1 cut was "volume control, manual host/port entry,
Denon only". That got scrapped partway through planning because:

1. Forcing manual IP entry on first launch is a terrible first
   impression for an app whose north star is *instant, fluid,
   modern*.
2. Half of the plausible user base has AVRs exposed via Home
   Assistant, not directly on the LAN. A wizard that only saw one
   of those would miss them on day one.
3. If we were going to add HA as a second backend eventually anyway,
   bolting it on *after* baking a concrete Denon Telnet target into
   every layer would be a rewrite. Make it an abstraction *now*.

So M1 grew a full wizard: discovery → HA connect (conditional) →
unified picker → test connection → done. Six screens, two discovery
services, one abstract `VolumeTarget` with two implementations. This
roughly doubled M1's code surface but made every subsequent milestone
cheaper.

## Key decisions

### Abstract `VolumeTarget` from day one

An interface with `connect`, `disconnect`, `setVolume`,
`observeConfirmed`, `observeConnection`. Two M1 implementations:
`DenonDirectTarget` (Telnet ASCII on TCP :23, persistent, push via
unsolicited `MV` events) and `HomeAssistantTarget` (HA REST for
commands, HA WebSocket subscribing to `state_changed` for push). The
volume view model consumes an injected target — it has no idea
whether it's talking to a Denon directly or to Home Assistant.

*Why:* two discovery sources into one picker is incoherent without
this abstraction. Retrofit-later would be painful.

### Home Assistant auth: long-lived access token, not OAuth

User pastes a token from their HA profile page. Stored in the
platform's secure store (Keychain on iOS, EncryptedSharedPreferences
on Android).

*Why:* OAuth requires a web flow, refresh tokens, and a client
secret. For a first release, LLAT is one paste and done. OAuth can
come later if the friction is real.

### HA host discovery: mDNS first, manual URL fallback

HA publishes `_home-assistant._tcp.local.`, so the wizard tries
mDNS first. If nothing shows up (carrier Wi-Fi, client isolation,
split subnets), the user types a URL. Manual entry is equal-weight
on the screen, not buried.

*Why:* mDNS on mobile networks is famously flaky, and we refuse to
dead-end a user whose network is being weird.

### Denon discovery: SSDP + mDNS, both tried

Denon/Marantz AVRs announce over SSDP (UPnP discovery) and, on
newer models, over mDNS. Both legs run in parallel; results stream
into the picker as they arrive.

*Why:* SSDP is the universal lane. mDNS is a shortcut for the
models that support it. Running both is cheap.

### Deduplication strategy

If the same AVR shows up via both Denon direct *and* Home Assistant
(matched on IP + model name), the picker shows one row with a
combined "direct + via Home Assistant" tag. On selection, it
defaults to the direct transport for latency reasons.

*Why:* avoids confusing "I have two Denons" illusions and defaults
to the lower-latency path.

### HA volume set + push

Commands: `POST /api/services/media_player/volume_set` with a
`volume_level` in 0.0–1.0. Push: subscribe to the WebSocket
`state_changed` event for the bound entity. Both are native HA APIs
with no proprietary glue.

*Why:* this gives HA-backed targets the same dual-value UX parity
(fast local intent, confirmed catches up) as the Denon direct
target. Without the WebSocket subscription we'd have to poll — which
would wreck the feel.

### Throttling: ~100 ms during drag, trailing-edge send on drag end

While the user is dragging, outgoing `MV{xx}` commands are rate-
limited to at most one per ~100 ms, then a final command always
fires when the drag ends so the device lands exactly on the intent
value.

*Why:* balances fluid drag feel against not flooding the protocol.

### Re-runnable wizard from settings

The onboarding wizard isn't a one-shot. The settings screen has a
"Change volume target" entry that re-runs the same flow.

*Why:* users move house, buy new receivers, change HA topology.
The wizard is the only configuration surface — make it accessible.

## What's in, what's out

### In M1

Two minimal native apps (`alloy-ios`, `alloy-android`); the
onboarding wizard; the volume control screen; two target
implementations; two discovery services; settings with a re-runnable
wizard entry; unit tests for state machines, protocol codec, HA API
mapping, and the discovery combiner; per-app README and CI.

### Out of M1

Every other feature section (ezBEQ, MiniDSP direct, ezelemental,
audio description, media player, media browser). OAuth. HA
discovery of non-AVR entities. Multiple targets bound at once.
Pro/subscription scaffolding (deferred to M2). App Store / Play
Store distribution (TestFlight / internal only). Haptic curves /
hold-to-repeat / dark mode / localization. HEOS CLI protocol.

Each deferral has a reason — mostly "wrong milestone, not wrong
idea".

## Open questions carried forward

- **HEOS-only models.** If a user has a Denon model that doesn't
  expose Telnet, we'll need the HEOS CLI protocol (TCP :1255, JSON
  framing). Deferred until someone actually hits it.
- **OAuth vs LLAT long-term.** LLAT works but isn't ideal. If we
  hear real friction from testers, promote OAuth to a later
  milestone.
- **SSDP device descriptor variations.** Different Denon/Marantz
  models have quirky descriptors. As we encounter quirks, they get
  documented in [`specs/denon-telnet.md`](../../../specs/denon-telnet.md).
- **Dual-native drift.** The shared spec is the anti-drift weapon,
  but the AI-transpile workflow hasn't been stress-tested yet. M1
  is the first real test.
- **Pro gating scaffolding timing.** The product plan says "day one
  of the first release". M1 is a dev milestone, not a release, so
  the scaffolding is deferred to M2 with no features behind it yet.
